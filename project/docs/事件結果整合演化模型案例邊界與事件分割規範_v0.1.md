## 文件定位

本文件用於定義「事件結果整合演化模型」在資料解析階段中，如何判定：

1. 一組人機互動紀錄是否屬於同一案例（Case）。
2. 不同事件（Event）之間是否具有關聯。
3. 何時應建立新的案例。
4. 如何避免不同任務、不同目的、不同狀態被錯誤整合。

本規範作為：

- 資料解析器（Data Parser）
- AI 任務分析系統
- 人機互動紀錄轉換流程

之前置邊界判定規則。

---

# 第一章　核心概念定義

## 1.1 案例（Case）定義

案例（Case）不是單純的一段對話。

案例定義：

> 在特定目標、特定問題、特定任務脈絡下，由多個事件組成的完整資料集合。

案例包含：

```
Case

 ├── Event
 │
 ├── State
 │
 ├── Task
 │
 ├── Feedback
 │
 └── Evolution Rule
```

案例是事件集合，不是文字段落。

---

## 1.2 事件（Event）定義

事件是案例中的最小可觀測資料單位。

事件定義：

> 在特定時間序列中，可被識別的人類輸入、AI 回應、系統結果或任務結果。

例如：

事件：

```
使用者提出需求
```

不是案例。

它只是：

```
Event_001
```

---

案例：

```
建立 AI 任務控制協議
```

可能包含：

```
Event_001
提出需求

Event_002
討論架構

Event_003
修改規範

Event_004
確認版本
```

---

# 第二章　案例建立原則

## 2.1 單一案例成立條件

一組事件必須同時符合以下條件，才可歸入同一 Case。

---

## 條件一：目標一致性（Goal Consistency）

事件是否服務於同一個主要目標。

例如：

同一案例：

```
建立事件結果整合演化模型資料庫
```

包含：

- 討論資料表
- 討論欄位
- 討論 Parser

成立。

---

不同案例：

```
建立資料庫
```

之後突然：

```
討論 AI 影像生成工具
```

不成立。

應分割。

---

## 條件二：任務一致性（Task Consistency）

事件是否屬於同一任務鏈。

判定：

```
事件 A
      ↓
事件 B
      ↓
事件 C
```

如果 B 是 A 的下一步，則保持同案例。

如果 B 是新的任務開始，則建立新案例。

---

## 條件三：狀態延續性（State Continuity）

後續事件是否修改、補充或完成前一事件形成的狀態。

例如：

事件：

```
目前 Parser 缺少案例分割規則
```

下一事件：

```
建立案例分割規範
```

狀態延續。

同案例。

---

如果：

事件：

```
討論 Parser
```

下一事件：

```
討論電影推薦
```

無狀態延續。

新案例。

---

# 第三章　事件分割規則

## 3.1 Event 不等於訊息

一個使用者訊息不一定是一個 Event。

原因：

單一訊息可能包含多個事件。

例如：

使用者輸入：

「昨天測試失敗，今天重新設計架構，現在準備建立新版。」

應拆成：

```
Event 001
昨天測試失敗

Event 002
重新設計架構

Event 003
建立新版
```

---

## 3.2 Event 分割觸發條件

符合以下任一條件，應考慮拆分 Event：

### A. 時間跳躍

例如：

```
昨天發生 A

今天執行 B
```

---

### B. 行為主體改變

例如：

```
使用者提出需求

AI 執行分析
```

分別建立事件。

---

### C. 任務目的改變

例如：

```
分析問題

↓

設計產品
```

若目的不同，需要重新判定。

---

### D. 結果狀態改變

例如：

```
未完成

↓

完成

↓

驗證通過
```

每個狀態變化可形成事件。

---

# 第四章　多案例判定規則

## 4.1 新案例建立條件

符合以下任一條件：

建立新的 Case。

---

### 1. 任務目標完全改變

例：

```
CASE001
建立 AI Parser

CASE002
設計 UI 介面
```

---

### 2. 原案例已完成

若：

```
Task Completed
Feedback Received
```

後續新的行動不再延續原任務。

建立新案例。

---

### 3. 無法建立事件關聯

若：

```
Event A

無法連結

Event B
```

則：

```
Need_Human_Confirm
```

不得強制合併。

---

# 第五章　案例合併規則

不同 Case 不得任意合併。

只有符合：

```
共同目標
+
共同任務鏈
+
共同狀態演化
```

才允許合併。

---

合併後必須保留：

- 原 Case ID
- 原 Event ID
- 合併原因

避免資料來源消失。

---

# 第六章　Parser 執行流程

AI 解析流程：

```
Conversation Context

        ↓

Event Extraction

        ↓

Event Boundary Check

        ↓

Case Boundary Check

        ↓

建立 Case

        ↓

建立五張核心資料表
```

---

# 第七章　驗證輸出要求

Parser 必須輸出：

【案例邊界判定】

包含：

- 是否單一案例
- 是否存在多主題
- 是否拆分案例
- 判定依據

---

格式：

```
Case Boundary Status:

PASS
/
Need_Human_Confirm

Reason:

[說明原因]
```

---

# 第八章　限制原則

Parser 不得：

1. 因為文字相似而合併案例。
2. 因為時間接近而合併案例。
3. 因為使用同一工具而合併案例。
4. 因為同一使用者提出而合併案例。

案例判定必須依據：

```
目標
+
任務
+
狀態
+
結果鏈
```
