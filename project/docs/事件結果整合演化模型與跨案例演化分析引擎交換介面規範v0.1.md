## 文件定位

本文件定義「事件結果整合演化模型資料解析器（Data Parser）」與「跨案例演化分析引擎（Evolution Engine）」之間的資料交換介面規範。

本介面目的為：

1. 將已完成結構化解析之案例資料轉換為可供演化分析使用的標準化候選資料格式。
    
2. 明確區分「資料解析」與「演化推理」兩個不同責任層。
    
3. 防止 Parser 在未具備充分證據時自行產生演化規則。
    
4. 提供 Evolution Engine 判斷資料是否具備跨案例分析資格所需之 Metadata。
    

本文件不定義：

- 演化規則生成演算法。
    
- 跨案例因果推理方法。
    
- 知識圖譜建立方式。
    
- AI 自動改善策略。
    

上述功能屬於下游 Evolution Engine 責任範圍。

---

# 1. 系統角色分工

## 1.1 Data Parser 責任

Data Parser 負責：

- 從人機互動紀錄中抽取事件資料。
    
- 建立 Event → State → Task → Feedback 之結構鏈。
    
- 驗證來源類型與資料狀態。
    
- 判定是否具備演化分析輸入資格。
    
- 輸出 Evolution Candidate Interface 資料。
    

Parser 不負責：

- 判斷是否形成通用規律。
    
- 建立 New_Rule。
    
- 評估模式價值。
    
- 進行跨案例推論。
    

---

## 1.2 Evolution Engine 責任

Evolution Engine 負責：

- 接收多筆 Evolution Candidate Interface。
    
- 執行跨案例比對。
    
- 建立 Pattern Evidence。
    
- 判斷是否形成 Evolution Rule。
    
- 產生演化模型結果。
    

Evolution Engine 不應直接讀取未經 Parser 驗證之原始對話資料。

---

# 2. Interface Flow

標準資料流：

```
Conversation Context
        ↓
Data Parser
        ↓
Event Table
        ↓
State Table
        ↓
Task Table
        ↓
Feedback Table
        ↓
Evolution Candidate Interface
        ↓
Evolution Engine
        ↓
Evolution Rule
```

禁止：

```
Conversation Context
        ↓
Evolution Engine
```

或：

```
AI Response
        ↓
Evolution Rule
```

---

# 3. Evolution Candidate Interface 定義

## 3.1 Interface Object

每一筆 Candidate Interface 必須代表：

「一組已完成解析、具備事件鏈追溯能力，但尚未形成演化規則的案例資料單位。」

---

## 3.2 基本欄位

|欄位|說明|
|---|---|
|Evolution_Candidate_ID|候選資料唯一識別碼|
|Case_ID|原始案例識別碼|
|Knowledge_Context_ID|所屬知識脈絡索引|
|Context_Model|原始資料類型|
|Parser_Status|Parser 驗證狀態|

---

# 4. Evolution Candidate Data Schema

## Evolution_Candidate_Table

### Evolution_Candidate_ID

格式：

```
CASE_ID-EVO-CAN-001
```

用途：

識別單一演化候選資料。

---

### Candidate_Evidence_Chains

格式：

```
Chain_1:
EVT-001
→ STA-001
→ TSK-001
→ FBK-001
```

用途：

提供 Evolution Engine 追溯來源。

限制：

- 必須引用實際存在資料 ID。
    
- 不得由 Parser 自行建立推論鏈。
    

---

### Observation_Count

定義：

目前可取得之獨立事件結果鏈數量。

範例：

```
Observation_Count = 1
```

代表：

存在單一完整案例鏈。

```
Observation_Count = 3
```

代表：

存在三組可比較案例鏈。

注意：

Observation_Count 不代表已形成演化規則。

---

### Temporal_Order

定義：

提供案例鏈時間排序資訊。

範例：

```
Chain_1 (2026-01)
before
Chain_2 (2026-02)
```

用途：

供 Evolution Engine 分析時間演化關係。

---

### Ready_For_Evolution_Engine

型態：

```
TRUE / FALSE
```

判定：

TRUE 必須同時符合：

1. Observation_Count >= 2
    
2. 具備 Temporal_Order
    
3. 所有必要鏈條資料狀態為 CONFIRMED
    
4. 無 BLOCKED 狀態
    

FALSE：

代表資料尚不足以進入演化分析。

---

### Evolution_Interface_Status

狀態：

## READY

條件：

資料可直接交由 Evolution Engine 處理。

---

## PENDING_PATTERN

條件：

已有完整案例鏈，但缺少跨案例樣本。

範例：

```
Observation_Count = 1
Required_Additional_Cases = 1
```

---

## NOT_AVAILABLE

條件：

包含：

- LIVE_CONVERSATION 尚未完成。
    
- 上游鏈條阻斷。
    
- 關鍵資料不足。
    

---

# 5. Source 與 Data Status 規範

Evolution Candidate Interface 不可改變上游資料來源權限。

## 允許：

|Source_Type|Data_Status|
|---|---|
|HUMAN_CONFIRMED|CONFIRMED|
|SYSTEM_RESULT|CONFIRMED|
|HUMAN_OBSERVED|RAW / UNCONFIRMED / CONFIRMED|

---

## 禁止：

AI_GENERATED → CONFIRMED

AI_GENERATED → Evolution Candidate Evidence

---

Parser 產生之 Candidate Interface 本身屬：

```
Source_Type = DERIVED
Data_Status = DERIVED
```

但其引用內容必須保持原始來源追溯。

---

# 6. Validation Requirements

Evolution Candidate Interface 輸出前，Parser 必須完成：

## 6.1 Chain Integrity Check

確認：

```
Event_ID
↓
State_ID
↓
Task_ID
↓
Feedback_ID
```

是否完整存在。

---

## 6.2 Evidence Check

確認：

- 是否存在來源證據。
    
- 是否存在非法推論。
    
- 是否混入 AI 生成內容。
    

---

## 6.3 Readiness Check

輸出：

```
Evolution_Readiness_Check:
READY
/
PENDING_PATTERN
/
NOT_AVAILABLE
```

---

# 7. 與 Evolution Rule 的邊界

Evolution Candidate：

代表：

「具備分析資格的資料」。

Evolution Rule：

代表：

「經過跨案例分析後形成的抽象規則」。

兩者不可混用。

禁止：

Parser：

```
Candidate → Rule
```

合法：

```
Candidate
+
Candidate
+
Candidate
↓
Evolution Engine
↓
Evolution Rule
```

# 8. 版本相容規範

Interface Version：

```
Evolution Candidate Interface Specification v0.1
```

獨立於：

- Parser Version
    
- Database Schema Version
    
- Evolution Engine Version
    

Parser 更新：

例如：

```
Parser v1.8
Parser v1.9
Parser v2.0
```

不代表 Interface 必須同步升版。

只有以下情況需要更新 Interface：

1. 欄位新增。
    
2. 欄位語意改變。
    
3. 資料交換流程改變。
    
4. 相容性破壞。
    

---

# 9. 設計原則總結

本介面遵守：

1. Parser 負責還原資料。
    
2. Evolution Engine 負責產生演化。
    
3. Candidate 是資料橋接層，不是規則層。
    
4. Evidence 優先於推論。
    
5. 未確認資料不得進入演化推理。
    
6. 單案例只能形成候選，不形成通用規則。
